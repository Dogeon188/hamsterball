# vector_env.py (gpu)

## Purpose

The Warp vector env: `gymnasium.make_vec(<id>, num_envs=N, vectorization_mode="vector_entry_point", backend="warp", ...)` returns a `gymnasium.vector.VectorEnv` that steps N worlds on one Warp device, each on a (level, task) it draws from a level bank, with actions, observations, rewards and flags as float32 torch tensors on that device. It wraps the batched core ([batch_core.md](batch_core.md)) with the env-step kernels ([env_step.md](env_step.md)). The CPU env ([env.md](../env.md)) stays the reference.

## Interface

Needs the `gpu` extra (`mujoco-warp`, `warp-lang`, `torch`); importing the module without it raises `ImportError` naming the extra, and `make_vec(backend="warp")` imports it lazily, so a plain install never loads Warp or torch.

- `WarpVectorEnv(num_envs, tasks=TASKS, levels=None, tier="abstract", camera_action=False, views=(), view_size=(84, 84), obs_state=True, frame_skip=10, time_limit_s=None, truncate=True, shaped=False, shaping_gamma=0.99, model_cache=16, difficulty=0.5, bank_size=1024, device="cuda:0")`: the CPU env's kwargs plus `bank_size` and `device`. `model_cache` is accepted and ignored (registered ids pass it; there is one compiled model). `bank_size` is the number of levels a generator pool draws into its bank (default 1024; see below). `device` is `"cuda:N"`, or `"cpu"` for Warp's CPU device (tests); a CUDA device that doesn't exist raises `RuntimeError`.
- `single_action_space`, `single_observation_space`, and the batched `action_space` and `observation_space` equal the CPU env's for the same kwargs (`Dict(state=Box(21), goal=Box(10))`). `metadata["autoreset_mode"]` is `SAME_STEP`.
- `levels`: a list of bundled names, paths, directories or `Level`s, or a `LevelGenerator`. A file pool's bank is every level in it; a generator pool's is `bank_size` levels drawn from the generator at the current difficulty, each with a task drawn uniformly among the env's `tasks` the generator supports and a seed, both from `np_random`, at construction and at each `set_levels()`. Bodies, seesaws and collapsing tiles in a pool raise `NotImplementedError`.
- `reset(seed=None, options=None)`: resets every world onto a drawn (level, task); `seed` reseeds the device RNG (and `np_random`). `options` may hold `level_index` and `task_index`, each an int or a `(num_envs,)` tensor with -1 for free, forcing a world's draw; a forced draw the pool can't make, or any other key, raises `ValueError`. Options apply to this reset only, and the same-step autoreset always draws freely. Returns `(obs, info)` with `info["level_index"]` and `info["task_index"]`.
- `step(action)`: `action` is `(num_envs, action dim)`, a torch tensor or array, with `turn` and `cam_pitch` last under the camera flag. Returns `(obs, reward, terminated, truncated, info)` as tensors: `obs` a dict `state` `(N, 21)` and `goal` `(N, 10)`, `reward` float32, the flags bool. `info`: `success` (bool), `failure_reason` (int32, the code table in [env_step.md](env_step.md), `left_region` included), `reward_terms` (`event`, `time`, `shaping`), `level_index`, `task_index`, and for the same-step autoreset `final_obs` (a dict of `(N, ...)` tensors, valid where the mask is true), `final_info` (`success`, `failure_reason`, `reward_terms` of the step that ended), and the bool masks `_final_obs` and `_final_info`. A world that finished has already reset when `step` returns: `obs` is its next episode's first observation, while `reward`, the flags and `info` describe the step that ended it.
- `step_to(core_states)`: `(num_envs, state size)` CPU-layout core states (numpy or torch), loaded into the worlds, then the env-step logic and autoreset with no physics; returns what `step` returns. It is the batched twin of `HamsterballEnv.step_to`, and the seam the parity tests use.
- The returned tensors are views of buffers the next `reset`, `step` or `step_to` overwrites; clone what you keep.
- Supported now, and the rest raises: all five tasks with still and moving markers and hazards (a drifting or spinning region, sweeping hazards), the abstract tier, no views, no bodies or tiles. Views, `tier="articulated"`, a body or tile level, and a marker attached to a body in an entry the env's `tasks` can draw raise `NotImplementedError` (`ValueError` for `obs_state=False` and a non-default `difficulty` on a file pool, as on the CPU); an unknown kwarg is a `TypeError`.
- `env.levels`: bank entry i's canonical `Level`, which reloads (`Level.from_yaml(level.canonical())`) to the same id. A level with no task among the env's `tasks` keeps its index but is never drawn.
- `set_levels(levels, difficulty=None)`: replaces the pool as the CPU env does (a generator, or a list; a file pool takes only the default difficulty). It rebuilds the bank: the padded model is recompiled, every table reuploaded and the step graph recaptured (about 2 s for a 1024-level bank of hfields on the CPU device, plus the generator's own time to make the levels, 13 s for 1024; the first step after it recaptures the graph on CUDA), so call it between rollouts. A world mid-episode keeps its state and finishes the episode on the level it was on (carried into the new bank as an entry that can't be drawn, unless the new pool holds that same `Level` object), with `level_index` -1 until it resets onto the new pool.
- Level sampling: a seeded per-world device RNG draws the level uniformly among the pool levels that have an entry for the forced task (any of the env's `tasks` if free), then the task uniformly among that level's own tasks that the env allows, as the CPU env's `_draw` does for a file pool.

## How it works

`BatchCore` holds the physics. `step` copies the action, then `BatchCore.step(..., post=self._env_step)` launches the n physics steps and `_env_step` in one captured graph on CUDA (eager on the CPU device): refresh the derived quantities (`mjw.kinematics`, `com_pos`, `com_vel`, `subtree_vel`, which the CPU's `_observe` also recomputes), the tier's `obs`, the `advance` kernel, `observe` into `state` and `goal`, `stash_final` for finished worlds, `BatchCore.reset_masked` on the finished worlds, `reset_episode`, and `observe` again for those worlds. Nothing syncs with the host. The step limit is `ceil(time_limit_s / (frame_skip * dt))`, as on the CPU. The draw, `set_spawn` and the level load sit ahead of every reset (the first from the host's `reset`, the autoreset's inside the graph). Per-entry tables (spawn pose and yaw, kill plane height, step limit, the marker rows, and each task's mode, goal row, survive flag and time penalty) are indexed by each world's entry. Each env step ends with `_look`: `look_markers` writes the world's task's marker colours into the model's per-world `geom_rgba` at the slots that hold its marker rows, and `pose_movers` puts each moving marker's slot geom at its pose at the world's sim time (`geom_pos`, `geom_quat`, and the static geom's `geom_xpos` and `geom_xmat`; see [env_step.md](env_step.md)); the same call follows every reset and `set_levels()`. `advance` keeps `prev_t`, the sim time of the previous env step, for the hazards' relative path. The step's time penalty is 0 for survive. 

## Invariants and checks

- Seam 2: `tests/test_warp_env.py` (reach_goal) and `tests/test_warp_tasks.py` (the other four tasks, and the colours) record CPU episodes (goals and hazards as sphere, capsule and box, falling off, truncation, `truncate=False`, shaping), replays their core states through the CPU-recorded and Warp `step_to`, and compares observations and rewards at `rtol=1e-5, atol=1e-5` and flags, success and failure code exactly; a finished world's `final_obs` equals the CPU's last observation.
- Seam 2 with moving markers (`tests/test_warp_movers.py`): CPU episodes of `survive_drift`, `survive_sweepers`, a generated level with a drifting region and two moving hazards (a hazard hit, a region exit, a time-up success, a shaped one), a hazard that jumps the still ball between two env steps, a spinning bar, and a box hazard on a path with spin replay through `step_to`, at the same bounds, with each moving marker's `geom_pos`, `geom_xpos` and `geom_xmat` compared to the CPU model's (capsules up to their axis's sign) on every unfinished step; four of them replay together on one mixed bank; and a live-physics check that each world's hazard geom sits at `motion.pose` of its own sim time.
- Seam 2 on a mixed bank (`tests/test_warp_levels.py`): six CPU episodes recorded on six different levels replay on worlds forced onto those levels of one bank (with an hfield level among them), and seven episodes of all five tasks replay on worlds forced onto their (level, task) of one bank, with the marker colours, at the same bounds; a ball stands on its own level's floor and falls off a level with none; draws cover the pool, honour the level's task list, replay under a seed; `set_levels()` swaps the pool under running worlds.
- `uv run --extra gpu pytest tests/test_warp_env.py tests/test_warp_tasks.py tests/test_warp_levels.py tests/test_bank.py` (skipped with a stated reason without the extra); `HAMSTERBALL_WARP_DEVICE=cuda:0` runs it on a GPU.

## Known quirks

- **Parity measured** (Warp CPU device, 2026-10-27, eight scenarios, 1 to 360 steps each): the largest observation difference was 5.7e-6 (float32 against the CPU's float64 on positions near 10 m), the largest reward difference 4.7e-8; flags, success and failure codes matched on every step. The 14 scenarios of the other four tasks (`test_warp_tasks.py`, up to 2,600 steps each): largest observation difference 7.6e-6, largest reward difference 1.6e-7, same exact matches, and the marker colours equal on every unfinished step.
- `info["failure_reason"]` is a tensor of codes, not the CPU's string.
- The tensors are views, see Interface.
- **CUDA run** (2026-10-27, Warp 1.18.0, an NVIDIA GeForce RTX 2080 Ti, sm_75, on a GPU cluster): `HAMSTERBALL_WARP_DEVICE=cuda:0 pytest -m gpu tests/test_warp_env.py tests/test_batch_core.py` passed, 38 of 38 (22 here, 16 of the batched core). The env step ran as one captured graph (physics, env-step kernels, autoreset). Parity differences matched the CPU device's: largest observation difference 5.7e-6, largest reward difference 4.7e-8.

## Decisions

- 2026-10-27, ticket gpu-backend/03: `info` and `final_info` hold the step that ended an episode; `final_obs` is a dict of `(N, ...)` tensors with masks rather than the CPU vector env's object array, since a per-world object array would force a host copy.
- 2026-10-27, ticket gpu-backend/03: one level and one task, so there is no device RNG and no reset options yet; both arrive with the level bank (ticket 05).
- 2026-10-27, ticket gpu-backend/04: a level that supports several tasks needs the task draw, so `tasks` had to leave one: the per-(level, task) tables and the device RNG came with ticket 05, which lifted that limit.
- 2026-10-27, ticket gpu-backend/03: a CUDA device that doesn't exist raises `RuntimeError` from `BatchCore`, which maps Warp's `ValueError` for an unknown device (ticket 02's doc had assumed it raised `RuntimeError`).
- 2026-10-27, ticket gpu-backend/05: `reset(options=)` takes `level_index` and `task_index` only (not the CPU env's `level` and `task` names or `difficulty`), as the spec says, and applies to that reset; the autoreset after it draws freely.
- 2026-10-27, ticket gpu-backend/05: `set_levels()` keeps running worlds on their old level through extra undrawable bank entries, rather than resetting them or leaving their geometry undefined; their `level_index` reads -1.
- 2026-10-27, ticket gpu-backend/05: the marker table, the mode, goal row, survive flag, time penalty, kill plane and step limit that ticket 04 held as kernel scalars are per-entry tables read through each world's entry; a world's marker slots hold only its own task's markers, so the other tasks' markers are not hidden by alpha as before.

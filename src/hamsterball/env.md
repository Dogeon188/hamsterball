# env.py

## Purpose

The Gymnasium env of spec §10 over the core: it picks a level and task per episode, steps the core, runs the marker tests in task order, and returns the `state` and `goal` observations, the reward (sparse, plus optional potential shaping), and `info`.

## Interface

- `import hamsterball` registers spec §2's six ids, each with `entry_point="hamsterball.env:HamsterballEnv"`: `Hamsterball-v0` (every kwarg free) and the presets `HamsterballReachGoal`, `HamsterballWaypointRace`, `HamsterballCollectItems`, `HamsterballUnlockGoal`, `HamsterballSurvive`, each fixing `tasks` to its one task. Registration, retired versions, and the `MUJOCO_GL` default are the package root's: see [__init__.md](__init__.md).
- `HamsterballEnv(tasks=TASKS, levels=None, tier="abstract", camera_action=False, views=(), view_size=(84, 84), obs_state=True, frame_skip=10, time_limit_s=None, truncate=True, shaped=False, shaping_gamma=0.99, model_cache=16, difficulty=0.5)`. `levels` is a `LevelGenerator` (such as `ProceduralGenerator()`, see [generator.md](core/generator.md)) or a list of `Level` objects, bundled level names (stems in `hamsterball/levels/`), level file paths, or directories (their `*.yaml`); `None` is every bundled level. `tasks` defaults to every task id (`TASKS`), so `gym.make("Hamsterball-v0")` with no kwargs constructs. Construction raises if no pool level (or the generator's `tasks`) supports any of `tasks`. `difficulty` goes to the generator; a value other than 0.5 with a file pool raises `ValueError`. `truncate=False` drops the time-up of every task but survive: the episode runs past its time limit until success or failure (see How it works).
- `env.tasks`, `env.tier`, `env.camera_action`, `env.frame_skip`, `env.time_limit_s`, `env.truncate`, `env.shaped`, `env.views`, `env.view_size`, `env.obs_state`: the constructor's values; the Collector writes the space-shaping and episode-ending ones into the dataset's `env_spec` (see [collector.md](data/collector.md)).
- `make_vec(num_envs, backend="cpu", **kwargs)`: every id's `vector_entry_point`, so `gymnasium.make_vec("Hamsterball-v0", num_envs=N, tasks=..., ...)` (mode `None` or `"vector_entry_point"`) calls it with the id's kwargs plus the caller's. It returns a stock `gymnasium.vector.AsyncVectorEnv` of `HamsterballEnv(**kwargs)` copies: `context="spawn"` on macOS and `"forkserver"` elsewhere, `shared_memory=True` only when `views` is non-empty, and `AutoresetMode.SAME_STEP` (the ended episode's observation in `info["final_obs"]`, its info in `info["final_info"]`). Worker i's env fn is `partial(hamsterball._worker_env, i, devices, cloudpickle.dumps(kwargs))`: with `devices = egl_devices()` above 1 (the Linux `/dev/dri/renderD*` count under `MUJOCO_GL=egl`, else 0) it sets `MUJOCO_EGL_DEVICE_ID` to `i mod devices` unless already set, then unpickles the kwargs and imports the env, so the id is set before the worker's first `import mujoco` (spec §11). `backend` other than `"cpu"` raises `NotImplementedError` (spec §15's `"warp"`). `vectorization_mode="sync"` or `"async"` never reaches it: Gymnasium builds its own `SyncVectorEnv`/`AsyncVectorEnv` from the entry point, with Gymnasium's defaults (next-step autoreset) unless `vector_kwargs` says otherwise.
- `env.set_levels(levels, difficulty=None)`: replaces the pool from the next reset, with the same entries and the same checks; `None` keeps a generator pool's current difficulty, and a file pool resets it to 0.5. On a vector env, `venv.call("set_levels", levels, difficulty=d)`.
- `reset(seed=None, options=None)`: `options` may hold `level` (a `Level` or canonical YAML string), `task`, and `difficulty`; see How it works.
- `env.unwrapped.step_to(core_state)`: one env step to a recorded core state, set with `Core.set_state` in place of stepping physics, then the rest of `step` as usual (marker tests, outcome, reward, observation, `info`). Re-render uses it (see [rerender.md](data/rerender.md)); it returns what `step` returns.
- `DiscreteAction(env)`: a wrapper with `Discrete(25)`: 0 is a no-op; `1 + 8·e + k` runs toward `k·45°` clockwise from camera forward (k = 0 forward, 2 right, 4 back) at effort `(0.25, 0.5, 1.0)[e]`. Under the camera flag `cam_yaw` stays 0.
- Action: the core's (`[run_x, run_y]`, plus `cam_yaw` under `camera_action`).
- Observation: `Dict(state=Box(19), goal=Box(10))`, float32, laid out as spec §10's tables, plus one `Box(0, 255, (H, W, 3), uint8)` per entry of `views` (see [core/views.md](core/views.md)). `obs_state=False` drops `state` and `goal`, and then needs at least one view.
- `close()` frees the renderers; the LRU keeps each level's compiled model and its renderer in one entry, so they evict together.
- An env with views raises under `MUJOCO_GL=glfw`; the package root sets the `MUJOCO_GL` default (see [__init__.md](__init__.md)).
- `info` on every step: `core_state`, `state`, `goal`, `success`, `failure_reason` (`None`, `"hazard"`, `"kill_plane"`, or `"left_region"`), `reward_terms` (`event`, `time`, `shaping`). On reset: `reset_options` (`{level: canonical YAML, level_id, task}`, plus `difficulty` for a generated level), `core_state`, `state`, `goal`.
- Bundled levels, at least one per task, each a box platform over a kill plane at −5 m:
  - `first_goal` (reach goal): 20 m square, goal sphere (1 m) 8 m along +y, 30 s.
  - `waypoint_loop` (waypoint race): 30 m square, four waypoint spheres looping round the spawn, 45 s.
  - `item_scatter` (collect items): 30 m square, three item spheres (0.8 m), 45 s.
  - `locked_goal` (unlock goal): 30 m square, two keys (0.8 m) to the sides, the goal 9 m ahead, 45 s.
  - `hill` (reach goal): `first_goal` with a 0.4 m round hfield hill (`hill.png`, 11×11, 5 m square) centred 4 m along +y, on the way to the goal.
  - `first_survive` (survive): 20 m square, a capsule region (radius 2 m, axis x = −1 to 1 m) around the spawn, 10 s.
  - `survive_drift` (survive): 20 m square, a 3 m square box region that walks a closed 24 m path (period 20 s, so 1.2 m/s) while spinning at 18°/s, 20 s. An inputless hamsterball leaves it at env step 83; the velocity-tracking controller of `tests/test_motion.py` survives the 1200 steps.
  - `survive_pushers` (survive): 16 m square, a sphere region (3.5 m) round the spawn, and two 3 m kinematic bars (orange) sweeping across it, one along x (amplitude 5 m, period 6 s) and one along y (5 m, 9 s), 20 s. An inputless hamsterball is shoved out at env step 123 (`left_region`). Play-test pending: whether stepping aside dodges the bars often enough.
  - `survive_collapse` (survive): no floor, a 9×9 grid of 1.5 m collapsing tiles (1 s delay) inside a 13.5 m square box region, 15 s. An inputless hamsterball falls with its tile and leaves the region below it at env step 99 (`left_region`). Play-test pending: whether 81 tiles and a 1 s delay leave a 15 s route.
  - `survive_sweepers` (survive): 20 m square, an 8 m square box region for 15 s, crossed by two 0.6 m balls oscillating 3.5 m along x (period 6 s) and along y (period 8 s) through its centre, and a 3 m bar spinning at 45°/s in the (−x, −y) corner. An inputless hamsterball is hit at env step 81 (`hazard`); the controller of `tests/test_moving_hazards.py` that rolls to (2.5, 2.5) and holds survives the 900 steps.
  - `survive_raft` (survive): a 4 m square raft (`body0`) with nothing under it, drifting round a 6 m square loop at 0.75 m/s and rocking up to 8° about the diagonal (period 7 s), with a box region (4 m square) attached to it, 30 s. An inputless hamsterball rolls off at env step 177, 2.95 s (`left_region`); steering toward the region centre (the `track` controller of `tests/test_motion.py`) rides it out. Play-test pending.
  - `survive_seesaw` (survive): a 4 m square seesaw (`body0`, 20 kg) on a ball joint at its centre (stiffness 100 N·m/rad, damping 20, up to 15°), nothing under it, a box region (4 m square) attached, 30 s, spawn 1.1 m off the pivot at (1, 0.5). An inputless hamsterball tips it and rolls off at env step 84, 1.4 s (`left_region`); the `track` controller (steer toward the region centre) balances it the 30 s, with the seesaw at its 15° limit early on and 7.9° on average after 2 s, the shell within 0.66 m of the pivot. Play-test pending.

## How it works

- Reset: options override kwargs, and the env draws each missing field from `np_random`, level first (spec §10): `{level, task}` as given; `{task}` a pool level supporting the task (whether or not the task is in `tasks`); `{level}` an allowed task the level supports, else any task it supports; `{}` a pool level supporting an allowed task, then an allowed task. A level that lacks the task, or a `{task}` no pool level supports, raises `ValueError`. `info['reset_options']` replays the episode on any env, whatever its kwargs.
- Generator pool: with no `level` option, the env draws a 63-bit seed (`np_random.integers(2**63)`), then the task if none is given (an allowed task the generator supports; a given task must be one of the generator's `tasks`), and calls `generator(task, seed, difficulty)` with `options['difficulty']` or else the env's difficulty. A `level` option skips the generator, as with a file pool. A `difficulty` option other than 0.5 raises with a file pool when the env would draw from it, and is ignored beside a `level` option.
- `reset_options['difficulty']`: the level's provenance `difficulty` when it has a `generator` block, else the difficulty the env passed to the generator, else absent. So a generated episode replayed from `{level, task}` on any env reports the same `reset_options`.
- Model cache: an LRU (`OrderedDict`) of `Core`s keyed by level id, at most `model_cache`; a hit moves the level to most recent, and a miss compiles and evicts the least recent. `Core.reset` calls `mj_resetData`, then places the shell at the spawn with the spawn yaw. The step limit is `ceil(time_limit_s / (frame_skip·dt))`.
- Targets: at reset the env lists the task's targets in task order as `(marker key, index)` pairs (`("goal", None)` for a lone goal). The live targets are the ones that can trigger now: the next waypoint only; every remaining key, and the unlock goal only once no key is left; every remaining item; the reach goal. The current target is the live target whose centre (`marker.centre`) is nearest the shell centre, and the fraction remaining is targets left over targets. Survive's one target is `("region", None)`, its centre the current target; its fraction remaining is `1 − steps / step_limit`, time left over the limit in whole env steps.
- Step: `Core.step(action, n=frame_skip)`, then the swept marker test from the previous env step's shell centre (a point at reset) against every live target, repeated until nothing new triggers, so one step completes waypoints i and i + 1, or the last key and the goal. Each waypoint, item, or key is +1; an empty target list is success, +1 more. Survive skips the swept test: its region is a point test on the current centre, and its target list empties (success) when the step count reaches the limit with the centre inside. Then failure, −1 added to that step's event, checked in order: a hazard (swept, every task; a moving hazard on the relative path from the previous env step's sim time to now, see [marker.md](core/marker.md)), the kill plane, and for survive leaving the region (`left_region`). Success wins over failure in one step. Reward is `event + time + shaping`, with time −0.001, or 0 for survive.
- Survive never truncates: at its step limit the shell is either inside (success) or outside (`left_region`), and both terminate.
- `truncate=False`: the step limit is still computed, but the truncation check is skipped, so a non-survive task never truncates; the time penalty stays. Survive is unchanged, since its limit is its success test, and no other task's observation reads the limit (its fraction remaining counts targets).
- Shaping (`shaped=True`): Φ = −0.01 × the distance from the shell centre to the current target (its centre), and Φ = 0 at a terminated state (success or failure; truncation isn't terminal). The step's term is `γ·Φ(s′) − Φ(s)`, where Φ(s) is the value stored at the previous step, so a target switch within the step shows as a jump.
- Movers: a marker with a `motion` ([motion.md](core/motion.md)) is read at the current sim time (`core.data.time`, part of the core state): the survive point test, the hazard test (which also reads `_prev_t`, the sim time of `_prev`, set at reset and each step, so `step_to` sets it from the stored state as well), the current target's centre (so the goal vector and shaping), and its look. Every `_observe` (reset and each step, `step_to` included) sets each moving marker geom's `geom_pos` and `geom_quat` to its authored values (snapshotted when the level compiles, in its `_Cached.movers`) moved by `motion.pose`; the geoms have no contact, so this changes no physics, and every view and the game window, which draw `core.model`, show it. The env sets `geom_sameframe` to `mjSAMEFRAME_NONE` on those geoms, since the compiler marks an unrotated world geom as sharing its body's frame and `mj_kinematics` then ignores `geom_quat`.
- Marker looks: marker geoms are named `<task>/<key>` or `<task>/<key>/<i>` (see [level.md](core/level.md)). Reset sets every marker geom's `rgba`: the episode task's markers take their kind's colour, other tasks' markers alpha 0, and the unlock goal and every waypoint after the first `LOCKED_RGBA` (grey, fainter). A collected item or key goes to alpha 0, a passed waypoint takes `PASSED_RGBA` (dim green) and the next waypoint the waypoint colour, and the unlock goal takes the goal colour when the last key is in. Episodes on a level share its cached model, so reset restores every look.
- Tile looks: every `_observe` blends each collapsing tile's authored colour (snapshotted at compile, `_Cached.tile_rgba`) toward `TILE_WARN_RGBA` by the fraction of its delay elapsed since the trigger, read from the core state, so it needs no reset and `step_to` draws it the same. Pixels only.
- Views: each level compiles with an offscreen buffer of at least `view_size` (and the game's 1280×720). Every env step, `views.pose` places the view mocaps (whether or not `views` is set, since the core state holds their poses). With views, `mj_kinematics` and `mj_camlight` carry the poses to the cameras, then one `mujoco.Renderer` per level, at `view_size`, held in that level's `model_cache` LRU entry beside its compiled core (an evicted entry closes its renderer) and with shadows off, draws each view with its `MjvOption`. The renderer is made lazily on the first render, so on the thread and in the process that steps the env.
- Observation: after stepping, the env recomputes derived quantities (`mj_kinematics`, `mj_comPos`, `mj_comVel`, `mj_subtreeVel`), which leaves the core state untouched. Vectors rotate into the camera yaw frame by −yaw about z; the shell's angular velocity first goes from the free joint's body frame to the world. Lean and relative velocity use the hamster subtree's centre of mass and its velocity, so an articulated tier reads the same.
- Attached regions: an attached survive region (ticket survive-movers/04) is tested and steered toward in its body's frame, which `_frame` reads from the body's joint qpos in the core state through `level.body_frame`: for a driven body that is its motion's pose plus a contact perturbation the next physics step discards (measured on `survive_raft`, inputless until it falls: at most 1.8e-7 m in position and 1.1e-7 in the quaternion), and for a seesaw (ticket 05) it is the pivot turned by the joint's qpos (a hinge's angle about its axis, a ball's quaternion), the only pose there is. The drawn region is a geom in the body, so it needs no posing.

## Known quirks

- The step-limit conversion subtracts 1e-9 before `ceil`, so a whole number of env steps doesn't round up through float error.
- Waypoints stay visible once passed, dim green; spec §7 hides only collected items and keys. Waypoints after the next show grey, since only the next can trigger.
- A marker test runs on the whole step's segment, not the part after the previous target, so a step that crosses waypoint i + 1 before i (in space) still counts both when it also crosses i.
- `action_space` comes from compiling the pool's first level, which takes one LRU slot. A generator pool has no level at construction, so the env compiles a throwaway `Core` on the default flat floor for it.
- Every generated level has its own id, so a generator pool misses the model LRU on every reset and compiles a model each time. Measured 2026-10-22 (ticket 10, reach goal and waypoint race): a reset, generation and compile included, takes about 6 ms at d = 0, 14 ms at d = 0.5, and 26 ms at d = 1; generated grids stay far under 256×256, so serialising the canonical form is cheap.
- The `MUJOCO_GL` default only takes effect if `hamsterball` is imported before `mujoco`.
- `egl_devices()` counts Linux render nodes and assumes EGL lists those GPUs first, in the same order; a machine where it doesn't (a software EGL device listed first) needs `MUJOCO_EGL_DEVICE_ID` set by hand, which the workers keep. Under forkserver, a main module that imports `mujoco` loads it in the fork server before the workers set the id; MuJoCo 3.x reads the id only at its first EGL context, so it still applies.
- `cloudpickle` comes with Gymnasium (its `AsyncVectorEnv` pickles env fns with it); the kwargs use it too, so a generator class defined in a test or notebook still reaches the workers.

## Decisions

- 2026-10-22, ticket hamsterball-v1/02: `env` is one module, not a package, until it needs a second file; `hamsterball.env:HamsterballEnv` resolves the same either way.

- 2026-10-22, ticket hamsterball-v1/03: markers of tasks other than the episode's hide (alpha 0), so a level that supports several tasks shows one task's targets. The spec says only that collected items and keys hide; this extends it.
- 2026-10-22, ticket hamsterball-v1/03: a failure step adds −1 to that step's other events rather than replacing them, since spec §9 sums the reward terms.

- 2026-10-22, ticket hamsterball-v1/07: the release named for a retired id is `hamsterball==<N>.*`, since spec §2 makes each N bump a major release and both start at 0; no release table to keep.
- 2026-10-22, ticket hamsterball-v1/07: a `{task}` reset option draws from the whole pool, not only levels with an allowed task, since options override kwargs.
- 2026-10-22, ticket hamsterball-v1/10: `reset_options['difficulty']` comes from the level's provenance when it has one, so replaying a generated episode from `{level, task}` on a file-pool env reports the same options; a `difficulty` reset option is ignored beside a `level` option and raises only when the env would draw from a file pool. Spec §10 says only that a non-default kwarg with a file pool raises.
- 2026-10-22, ticket hamsterball-v1/10: with a generator the env draws the seed before the task, as spec §10 orders level before task, though the generator needs the task to build the level.
- 2026-10-22, ticket hamsterball-v1/14: `make_vec` lives in `env.py` beside the env; the project owns no vector env (issue 23). Each worker builds its env from a `functools.partial(HamsterballEnv, **kwargs)`, which pickles under `spawn`; the renderer is already lazy, so it's made in the worker. `vectorization_mode="sync"` keeps Gymnasium's own path and next-step autoreset default rather than being forced to same-step, since Gymnasium never calls the entry point in that mode.
- 2026-10-22, ticket hamsterball-v1/09: `step` is the physics then `_advance()`; `step_to` swaps the physics for a stored core state, so re-render reuses the marker tests, marker looks, and view posing instead of copying them.
- 2026-10-22, ticket survive-movers/03: the env builds each `Core` from the `Level` itself (not its MJCF), so the core gets the level's kinematic bodies and their motions; the env does nothing else for bodies, which move in the core state and so in every view, the game, replay, and re-render.
- 2026-10-22, ticket survive-movers/04: the attached region's frame comes from the body's qpos, not its motion's analytic pose (ticket 03's suggestion), so a passive body (ticket 05) attaches the same way. Both are in the core state, so replay and re-render are unaffected.
- 2026-10-22, ticket survive-movers/05: the observation keeps spec §10's 19 state numbers, so a seesaw's tilt is not in the state vector. A policy sees it in pixels (the platform and the drawn region tip in every view) and, faintly, in the goal vector: the attached region's centre sits 0.7 m above the pivot on `survive_seesaw`, so it moves about 0.7·sin θ (6 cm at 5°) uphill as the seesaw tips. The ball's own lean and velocity are in the state, which is enough for `track` to balance it. Trade-off: a state-only policy has to infer the tilt from how the ball accelerates; adding the tilt (or the attached body's pose) to the state would change spec §10's shape for every level, so it waits for a play-test or a learning result that needs it.
- 2026-10-22, ticket survive-movers/06: a tile's warning look is derived from its trigger time each `_observe`, not set on events, so re-render needs nothing extra. `TILE_WARN_RGBA` is a look constant pending play-test.

## Tried and rejected

- 2026-10-22, ticket hamsterball-v1/03: a scripted controller that runs straight at the current target overshot every turn (fell off `waypoint_loop` after the first waypoint; ran out the clock on the other two). The tests use velocity tracking instead.
- 2026-10-22, code review of hamsterball-v1: gathering the per-task `if self.task == ...` checks (reset's locked goal, `_advance`'s survive point test, goal relight, time term and `left_region`, `_live`, `_observe`'s fraction remaining) into one per-task rule table. Survive's checks change control flow rather than pick a value, and the other tasks have one check each, so a table would hold more lines than the branches it replaces; not written.
